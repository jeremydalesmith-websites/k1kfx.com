WHAT THIS IS
------------
A web application (app) for running a "fox hunt" (amateur radio direction finding). It is a fox-hunt site your club hosts: every member hunts from their own phone, alone in a hunt of their own or together with others in a group hunt whose bearings land on one shared map. A club event may have one, a few, or many hunts running at once. Each participant enters their location and the bearing toward the strongest signal; the bearing lines converge on the hidden transmitter. It works on phones, tablets, and computers, runs offline once loaded, and is configured by editing plain-text files - no programming required.

You host it on your own web space (or on Google's free Firebase Hosting), backed by your own free Google Firebase project. Participants join with just a handle - no accounts, no passwords.  The application is designed to protect user anonymity. You, the host, get a private admin login for the admin panel and the analytics dashboard.

 SECTION 1 - BEFORE YOU BEGIN

1.1  WHAT YOU NEED
------------------
1.1.1  A free Google Firebase project. This provides participant sign-in, the shared hunt data, your admin login, and anonymous usage analytics. It is required on BOTH hosting paths.

1.1.2  Somewhere to serve the files. Either your own static web hosting (cPanel File Manager, FTP, or similar - no server-side programming is needed), or Google's free Firebase Hosting. See Section 1.2.

1.1.3  HTTPS. This is not optional. The app uses GPS, the compass, and offline caching, and browsers only permit those on a secure (https://) address. On plain http:// the map and compass will not work. Firebase Hosting provides HTTPS automatically; on your own host you must have it enabled.

1.1.4  A plain-text editor for four small configuration files (Notepad is fine; so is any code editor). You will change values inside quotation marks. You will not write any code.

1.1.5  A map for your area - hosted for you. The app's map is an offline vector map. Ready-made regional maps for most of the world are hosted on Fox Pursuit's map service and stream straight to the app - you do not download, extract, or host anything. You simply point the app at your region (Section 4.4). If you would rather host the map yourself, you can (Section 2.4) - and there are good reasons to, covered there. Section 2 explains both.

The site can live at your domain root or in a subfolder, for example https://yourdomain.com/foxhunt/.


1.2  CHOOSE YOUR HOSTING PATH
-----------------------------
There are two ways to publish the app. Decide as you read this section, because Sections 6 and 7 are alternatives - you will follow only one of them.

  PATH A - YOUR OWN WEB HOST.
  Choose this if you already have web hosting, or intend to get one. You upload the files with a File Manager or FTP client, the same way you would publish any web page. This is the simpler path, and it is the one this product is built and supported around.  But please note that this file provides only the configuration settings you will need to implement.  You will need to consult your hosting platform if you need assistance with site configuration (not app configuration).  This document cannot provide site support for all the various web hosts.

  PATH B - FIREBASE HOSTING (free).
  Choose this if you do NOT have web hosting and would rather not subscribe to any. Google will serve the app for free, out of the SAME Firebase project that already holds your database and sign-in, with automatic HTTPS. The trade-off is that you publish the site to the hosting from a command line rather than by dragging files into a File Manager. It is a handful of commands the first time, and a single command for every update after that. If you choose this path you will continue through Section 5, skip Section 6, then do Section 7.

Please read Section 7.1 before committing to Path B - it explains the limits of what this guide can promise about Firebase Hosting.

You can switch paths later. Nothing in the app itself is tied to either one.


1.3  THE FOUR FILES YOU OWN
---------------------------
Four files in this package hold YOUR settings. You will edit them in Section 4, and you must PRESERVE YOUR EDITS every time you install a newer build (Section 11):

     0-config-firebase.js  your Firebase credentials
     0-config-admin.js     your admin User ID list (ADMIN_UIDS)
     0-config-foxhunt.js   your branding, page content, units, thresholds
     0-config-license.js   your site key

The 0- prefix has no special meaning to the app (although it cannot be changed); it simply keeps these four files together at the top of a file listing so they are easy to find. They are the only files that carry your personal settings.

Every other file in the package can be replaced freely on an upgrade. Remember these four now; Section 11 will remind you.

BACK THEM UP. Copy all four somewhere off this computer - a cloud drive, a USB stick, an email to yourself - as soon as you have filled them in. They are small text files. Rebuilding them means re-fetching your Firebase credentials, re-finding your admin UID, redoing every customization, and digging your site key back out of your records. Taking five after you have customized the files to make a backup can save an afternoon of work later. If you self-host your map (Section 2.4), back up the .pmtiles file too; it is the one thing here you may not be able to re-download.

 SECTION 2 - YOUR MAP                           (both paths)

The app draws its basemap from an offline vector map (a .pmtiles file). You have two ways to supply it (2.1 or 2.4), and for almost everyone the first (2.1) is all you need.

  - 2.1  Use a hosted region (the quick path - recommended)
  - 2.2  What participants see, and offline use
  - 2.3  Map data and attribution
  - 2.4  Host the map yourself (optional - and why you might)
  - 2.5  Back up what you cannot re-download

A note on why 2.4 exists, before you decide: a widely used piece of ham radio software once came within weeks of disappearing worldwide when its sole creator died with no plan for its continuation. Fox Pursuit is built so that cannot happen to your installation. Self-hosting your map (2.4) means your app depends on nothing outside your own control - not this map service, not its maintainer. The quick path (2.1) below is easiest; self-hosting (2.4) is the durable one. Both are fully supported, and you can switch at any time by changing one line.  So, choosing the quick path now does not impose any risk of loosing your site later.


2.1  USE A HOSTED REGION (THE QUICK PATH - RECOMMENDED)
-------------------------------------------------------
Ready-made regional maps are hosted for you at https://maps.foxpursuit.com and stream to the app over the network - no download, no extracting, no hosting, and no server configuration on your part. The service already answers HTTP Range requests and sends the required CORS headers, so it "just works."

2.1.1    Open the coverage map.  DO THIS NOW.  Go to:  https://foxpursuit.com/maps/
2.1.2    Find the area you hunt. Use the "Check my location" button to quickly navigate to your current location.
2.1.2.1  Note how the map boundaries overlap. This is to accommodate hunts that may occur in an area that overlaps from one area to the next.  Therefore, your location may be covered by one or more maps.  Select the one that fits your hunt area.
2.1.2.2  When selected, each region shows its name, such as:
         USA-MO_SSW

2.1.3  SAVE THE NAME shown for the area you selected.  That is all you need from this section - you will put it into tileUrl in Section 4.4.

That is the entire map setup. The map streams from the hosted service the next time the app loads.

2.1.4  The bundled sample. This package ships with tileUrl already pointed at a small local sample (Southwest Missouri, United States) in the maps/ folder, so the map works the instant you publish - even if you do not pick a region, and even with no connection on that first load. Leave it as-is to try things out; switch tileUrl to your region's address when you are ready.

If your hunt area is not yet covered, or you want a tighter/custom area, see 2.4 (host the map yourself) - you can build any region you like.


2.2  WHAT PARTICIPANTS SEE, AND OFFLINE USE
-------------------------------------------
The map behaves the same whether it streams from the hosted service or from your own copy.

2.2.1  Detail and zoom. Regional maps carry full street-level detail across the hunt area. Zoom in far enough and the map stops getting more detailed - it will not go blank on you.

2.2.2  Offline. Tiles are cached as they are viewed online, so anywhere a participant has panned while online is available offline. For deliberate offline use, the app's "Download / View Offline Maps" panel saves a chosen radius - or the whole region - into the device for use with no signal. Before heading into weak coverage, hunt participants can open the hunt area once with a connection (or use the download panel) so the tiles are stored on their device.

2.2.3  If you change the map later. If you point tileUrl at a different region, participants who had downloaded the old one will be prompted to refresh; the app detects the change and reloads cleanly.


2.3  MAP DATA AND ATTRIBUTION
-----------------------------
The map data is (c) OpenStreetMap contributors, licensed under the Open Database License (ODbL). Fox Pursuit displays this credit on the map automatically. You must keep it visible - do not remove or cover the OpenStreetMap attribution shown on the map. If you host or share the map file yourself (2.4), keep the ATTRIBUTION.txt that accompanies it. That is the whole of your licensing obligation to OpenStreetMap.  The app handles the visible part for you.


2.4  HOST THE MAP YOURSELF (OPTIONAL - AND WHY YOU MIGHT)
--------------------------------------------------------
You are never required to host the map - the quick path (2.1) covers most people. But hosting your own copy is fully supported, and there are two real reasons to:

  - Control: your map lives on your own host, on a domain you choose, with no dependence on an outside service being up.
  - Continuity: this is the important one. If the hosted map service ever goes away - or its maintainer stops supporting it, becomes unable to, or dies - a self-hosted installation keeps working indefinitely, because it depends on nothing outside your control. Hosting your own map (and keeping the file backed up, 2.5) is how you make your hunt outlast anyone, including the app creator.

You can either download a ready-made region and host it, or build your own.

2.4.1  Get a .pmtiles file.
  (a) Download a ready-made region: from the coverage map (2.1.1), use the region's download link to save its .pmtiles to your computer.
  (b) Or build your own with the free "pmtiles" tool, which extracts any rectangle of the world from OpenStreetMap-based Protomaps builds:
      - Get the tool from  https://github.com/protomaps/go-pmtiles/releases
      - Find your area's bounding box (min/max longitude and latitude) with a tool such as https://www.latlong.net/polygon-drawer or https://boundingbox.klokantech.com  (use the "csv"/"lng,lat" form).
      - Extract, for example:
    pmtiles extract https://build.protomaps.com/YYYYMMDD.pmtiles your-region.pmtiles --bbox=minLon,minLat,maxLon,maxLat --maxzoom=15
 (Use a current build date from https://maps.protomaps.com/builds/; older daily builds are removed and will fail.)
 Either way, keep the accompanying ATTRIBUTION.txt with the file (2.3).

2.4.2  Put it where the app can reach it.
  (a) Simplest: drop the .pmtiles into the app's own maps/ subfolder and set tileUrl to "maps/YOUR-REGION.pmtiles" (Section 4.4).
  (b) Or host it anywhere else (your own domain, a cloud bucket, a CDN) and set tileUrl to its full https address.

2.4.3  Your host must support two things (the hosted service in 2.1 already does):
       - HTTP Range requests (a 206 response). The app reads a few kilobytes out of the middle of the file rather than downloading the whole thing; a host that ignores Range returns the entire file and breaks the map. Nearly all web hosts, and Firebase Hosting, support Range out of the box.
       - CORS headers, IF the file is on a different domain than the app. It must send Access-Control-Allow-Origin and allow the Range request header and expose ETag/Content-Range. (Same-folder hosting per 2.4.2(a) needs none of this.)
       Use the admin page's "Check map hosting" button to confirm your file loads, answers Range, and (if cross-domain) sends CORS correctly.

2.4.4  Size. Keep a hosted piece reasonable (roughly under 100 MB) so the whole map can be saved for offline use in one step; larger files still work online and by radius download, just not as a single whole-map save.

2.4.5  A NOTE FOR THE FUTURE - map schema versions. The daily builds referenced in 2.4.1 follow a published map schema, and that schema is occasionally revised. This build of Fox Pursuit draws maps built to the PROTOMAPS BASEMAP v4 schema. Builds made to that schema will keep working forever, because your copy of the app and your copy of the map never change unless you change them.

  If, years from now, you build a new .pmtiles and the map opens but looks wrong - missing roads, unlabeled, oddly colored - you have almost certainly been given a NEWER schema than this app knows how to draw. That is a version mismatch, not a broken file, and there are two ways out:
  (a) Build from an older daily build made while v4 was current, or
  (b) Use a Fox Pursuit build updated for the newer schema, if one exists.

  Record this somewhere with your backups: THIS APP EXPECTS PROTOMAPS BASEMAP v4. It is the one piece of information that is obvious today and impossible to work out later.

2.4.6  IF THE MAP SERVICES THEMSELVES ARE GONE.
  Section 2.4.1 assumes two things still exist: this seller's hosted regions, and the Protomaps daily builds. Neither is under your control, so here is the path that depends on neither:

  The underlying map data is OpenStreetMap, which is a public, freely licensed database maintained by a global community and mirrored widely. Regional extracts have been published continuously by several independent providers for many years, and the tools to turn one into a .pmtiles file are open source.

  In outline: download a regional extract of OpenStreetMap data, then run an open-source tile builder over it to produce a .pmtiles archive. The Protomaps "basemaps" project publishes the exact build configuration used for the daily builds, so a rebuild can match what this app expects. It needs a reasonably capable computer and some patience - hours, not minutes, for a large area - but it needs no permission, no account, and no company's continued existence.

  You will not need this while the services in 2.4.1 are running. It is written down so that the option is known to exist, by someone who may be reading this long after the fact.


2.5  BACK UP WHAT YOU CANNOT RE-DOWNLOAD
----------------------------------------
Continuity only works if the pieces survive your device. Save these somewhere OFF the device - a password manager, a cloud drive, or a printout:

  - Your SITE KEY (the FP1. key in 0-config-license.js), which you will produce later, and your GUMROAD LICENSE KEY, which you received in your receipt email. Either one gets you back: the site key is what licenses the app, and the Gumroad key can always retrieve it again from setup.html. Save both.
  - Your four personalized files: 0-config-admin.js, 0-config-firebase.js, 0-config-license.js, and 0-config-foxhunt.js (Section 4).
  - If you self-host the map (2.4): your .pmtiles file(s) and ATTRIBUTION.txt.

With those in off-device backup, any installation can be rebuilt from scratch on any device, with or without us.

============================================================
 SECTION 4 - CONFIGURE THE FOUR FILES YOU OWN   (both paths)
============================================================
Edit these in a plain-text editor. Change only the VALUES inside the quotation marks. Do not rename the keys, and do not remove commas, quotes, or braces - a single missing character will stop the file from loading.


4.1  0-config-firebase.js  - YOUR FIREBASE CREDENTIALS
------------------------------------------------------
Paste the firebaseConfig values you copied in Section 3.4.6 into the firebaseConfig object. This is what connects the app to YOUR Firebase project.

CAUTION: the Firebase values go in 0-config-firebase.js, NOT 0-config-foxhunt.js. The two names are similar. 0-config-firebase.js holds "const firebaseConfig = {...}"; 0-config-foxhunt.js holds "const FOXHUNT_CONFIG = {...}" for branding and content.

The block looks like this:

    const firebaseConfig = {
      apiKey:            "YOUR_API_KEY_VALUE",
      authDomain:        "YOUR_AUTHDOMAIN_VALUE",
      projectId:         "YOUR_PROJECTID_VALUE",
      storageBucket:     "YOUR_STORAGEBUCKET_VALUE",
      messagingSenderId: "YOUR_MESSAGINGSENDERID_VALUE",
      appId:             "YOUR_APPID_VALUE"
    };

Easiest method: select the whole placeholder block above - from "const firebaseConfig = {" through the closing "};" - and replace it with the block Firebase gave you. The block Firebase gives you already includes its own closing "};". Keep every quotation mark, and be sure the closing "};" survives, because there is more code below it in the file.

About measurementId: you will only have this value if you enabled Google Analytics when creating the project, which this guide recommends against. If your pasted config has no measurementId line, that is correct and expected. This app never uses it. Its absence is not a missed step.

If you get this wrong, the app will load but sign-in will fail. The app recognizes the common setup errors and says so in plain language on the sign-in screen, with a link to the Troubleshooting page - you do not have to decode a raw Firebase error. Section 8.1 shows you how to confirm the file actually reached your server, which is the failure this step most often produces. See also Section 15.


4.2  0-config-admin.js  - YOUR ADMIN UID
----------------------------------------
Put the admin UID from Section 3.5.3 into the ADMIN_UIDS list BETWEEN the single-quote marks:

    const ADMIN_UIDS = [
      'YOUR_ADMIN_UID'
    ];

For more than one admin, see Section 10.2.


4.3  0-config-foxhunt.js  - YOUR BRANDING AND BEHAVIOR
------------------------------------------------------
This holds your brand name, page content, units, hunt length, bearing thresholds, theme, and more.

One value in this file IS required before the map will work - the map address, tileUrl, covered in 4.4 just below. Everything else here is optional: get the app running first, then personalize it using Section 9. The shipped defaults are sensible and the app will run as-is.


4.4  0-config-foxhunt.js  - YOUR MAP ADDRESS (tileUrl)   [REQUIRED]
-------------------------------------------------------------------
tileUrl, near the top of 0-config-foxhunt.js, tells the app where to find the map file you prepared in Section 2.

tileUrl tells the app where to find its map. For a ready-made hosted region (Section 2.1 - the quick path), use the region's full address, such as:

    tileUrl: "https://maps.foxpursuit.com/USA-MO_SSW.pmtiles",

For a map you host in the app's own maps subfolder (Section 2.4), use the folder and file name, such as:

    tileUrl: "maps/your-region-name.pmtiles",

This package ships with tileUrl set to the bundled sample ("maps/springfield-branson.pmtiles") so the map works the moment you publish.  To simplify implementation, it is suggested that you make no changes to the tileUrl value now, and publish the site with the default map.  After you have validated it is working then return to this section and change the tileUrl value to your region's address (hosted) or file name (self-hosted). If you host the .pmtiles on a different domain than the app, that host must answer HTTP Range requests and send CORS headers (Section 2.4.3); the hosted service already does both.

If tileUrl is blank or an invalid path, the app shows a "Map not configured" notice in place of the map, rather than a blank screen, so you can tell at a glance that this step requires correction.


4.5  0-config-license.js  - YOUR SITE KEY   [DONE LATER, IN SECTION 8.2]
-------------------------------------------------------------------------
LEAVE THE 0-config-license.js FILE ALONE FOR NOW. It is filled in after your site is published, because the page that issues your site key runs on your own site. Section 8.2 walks you through it and gives you the exact line to paste.

THE REMAINDER OF THIS SECTION IS INFORMATION ONLY.  DO NOT MAKE ANY CHANGES TO YOUR FILES.  YOU WILL MAKE THE CHANGES IN LATER SECTIONS.

TWO DIFFERENT KEYS - THIS TRIPS PEOPLE UP
  GUMROAD LICENSE KEY   Comes with your purchase, on your receipt. Looks like
                        1B686E58-DC7F46A8-9E8DCD48-062F41DC. This is your proof
                        of purchase. You paste it into setup.html in your
                        browser - you never edit that file in a text editor.

  SITE KEY              What setup.html gives you back. Begins with FP1. and
                        runs about 150 characters. THIS is what licenses your
                        site, and this is what goes in 0-config-license.js.

You will keep both. They are not interchangeable, and neither one replaces the other.

What will happen in Section 8.2:

The key travels with your site, so every phone and tablet that loads your pages is licensed automatically. Participants never enter anything. Replace a device, wipe a browser, or move to a different web host, and nothing has to be re-entered - the key is already in your deployment.

The check runs entirely inside the browser, using mathematics, with no license server and no internet connection. Nothing about it can stop working because a service was switched off, a company closed, or the author of this software is no longer around. Section 14 explains that in full.

You can confirm the key at any time by opening setup.html in your browser on your published site (Section 8.2).

Note the two directions of travel through that page: your GUMROAD LICENSE KEY goes IN, pasted into the page in your browser; the finished line for 0-config-license.js comes OUT, to be pasted into that file with a text editor. setup.html itself is never edited.

6.2  IF YOUR HOST AUTO-CREATES AN index.php
-------------------------------------------
For site security purposes some hosts automatically place an empty index.php file in every new directory. If that empty file is served ahead of index.html, visitors get a blank page instead of your site.

If you see an empty index.php in the folder, delete it before uploading.

If your host keeps putting it back, the reliable fix is to tell the web server to prefer index.html. On an Apache host, change this line "DirectoryIndex index.html" in your .htaccess file to "DirectoryIndex index.html index.php" (without the quote marks).

With that in place, a stray index.php can reappear as often as it likes and will never be reached.


6.3  NON-APACHE HOSTS
---------------------
Firebase Hosting ignores .htaccess, and so do non-Apache servers such as Nginx or IIS. If your host is not Apache, set the equivalent "no directory listing" option in its control panel, and make sure sw.js is not aggressively cached. See Section 13.

7.7  RESTORE firebase.json   *** CRITICAL - DO NOT SKIP ***
-----------------------------------------------------------
Look at the output of the command you just ran. Among the last lines you will see:

    +  Wrote configuration info to firebase.json

Read that carefully. "firebase init" OVERWRITES firebase.json, and it does so WITHOUT ASKING. It asked your permission before touching index.html, but it does not extend the same courtesy to firebase.json. It has just replaced the firebase.json included in this package with a short, generic one of its own.

Why this matters: the included firebase.json carries a required setting that tells Firebase never to cache sw.js, the service worker. Without that setting, browsers can hold on to a stale copy of your app, and ANY UPDATES YOU MAKE WILL NOT REACH YOUR USERS. Worse, nothing appears to be wrong - the site works, it is simply frozen on an old version. This is a silent failure, which is exactly why this step is called out so strongly.

TO FIX IT: copy firebase.json from your ORIGINAL DOWNLOAD of this package back into the app folder, overwriting the one init just wrote.

    The pristine copy is always sitting in the package you downloaded, so it cannot be lost. If you prefer, you can instead open firebase.json in a text editor and replace its entire contents with the correct version - but copying the file from the download is simpler and less error-prone.

THEN CONFIRM IT. The correct file contains a "headers" section that mentions sw.js. Check for it:

    In Command Prompt:
        findstr "sw.js" firebase.json

    In PowerShell:
        Select-String -Path firebase.json -Pattern "sw.js"

If it prints a matching line, the correct file is in place and you may continue. If it prints nothing at all, the generic file is still there. Copy the file again from the download and re-check. Do not deploy until this check passes.

    (You can also simply look at the file - "type firebase.json" in Command Prompt, or "Get-Content firebase.json" in PowerShell. The correct file is around 20 lines and contains a "headers" block naming sw.js and Cache-Control. The generic one init writes is roughly half that and has no "headers" block at all.)

    (Tip for next time: you can make a spare copy BEFORE running init - "copy firebase.json firebase.json.bak" in Command Prompt, or "Copy-Item firebase.json firebase.json.bak" in PowerShell - and restore from it afterward. But copying from the original download works even if you forget, which is why that is the method given here.)

9.2  BACKGROUND IMAGE (optional)
--------------------------------
Set background: "image" and point backgroundImage at a file you have placed with the app, for example "assets/background.jpg".

9.2.1  SMALLER IS BETTER. It loads on every page and is cached offline.
9.2.2  Maximum size is backgroundMaxKB (default 500 KB). A larger image is ignored and the grid is shown instead, with a note in the browser console.
9.2.3  Use JPEG or WebP for photographs, PNG for graphics. Around 1600-1920 pixels wide is plenty.
9.2.4  backgroundDim (0 to 1) washes the theme color over the image for readability. 0.6 is a good starting point.
9.2.5 backgroundSize (cover, contain, or repeat) decides how your image fills the screen, and which one you want depends on what kind of image it is.

  "cover" - scaled up until it covers the whole screen, with whatever hangs over the edges cropped off. Nothing shows through, but you never see the entire image, and how much is cropped differs between a phone held upright, a phone turned sideways, and a PC. Use it for photographs and large artwork, and keep anything that matters - a callsign, a logo - away from the edges, because on some screens it will be cut. The supplied foxtail_1x1.jpg is an example.

  "contain" - scaled until all of it fits on screen, so the whole image is always visible. Because it keeps its proportions there will be empty space above and below, or at the sides, filled with your theme color. Use it when the image must be seen complete, such as a club logo. Be aware that a wide image on a phone held upright ends up quite small in the middle of the screen.

  "repeat" - used at its own size and tiled across the screen like wallpaper. Use it for a small seamless pattern, roughly 100 to 300 pixels - a texture, a weave, a grid. It suits this well because a very small file covers any screen without scaling. A photograph tiled this way looks like a wall of postage stamps.

If you are unsure, start with "cover". It suits most images and is the default.

9.2.6 backgroundPosition decides which part of the image survives when "cover" crops it, and where the image sits within the empty space under "contain". "center" suits most images; "top" is useful when the top of the picture is the part you want kept.


9.3  LOGO / FAVICON
-------------------
The fox image is the single file favicon.svg. Replace it with your own and the logo changes everywhere at once - top bar, Home hero, buttons - along with the browser-tab icon.

9.3.1  Use an SVG. It is displayed at sizes from a tiny tab icon up to a large hero image. A PNG can be embedded inside an SVG if you need to.
9.3.2  Keep it roughly SQUARE, with a TRANSPARENT background, and keep the file small.
9.3.3  A favicon_foxtail.svg is included as an example. To use it, rename or delete favicon.svg, then rename favicon_foxtail.svg to favicon.svg.

 SECTION 10 - ADMIN GUIDE
============================================================

10.1  THE ADMIN LOGIN
--------------------
admin.html and analytics.html are protected by your email/password admin account. Open either page and sign in. There is no link to these pages from the app; you type their addresses directly.

Being signed in persists on that browser until you sign out, and the SAME login works on any device or browser, because its User ID (UID) never changes.

The admin login runs independently of the participant app. Signing in as admin never disturbs the app, and using the app never signs you out of the admin pages.

When signed out, those pages show only the sign-in box. When signed in, a small "Signed in as admin - Sign out" bar appears at the top.


10.2  ADDING MORE ADMINS
-----------------------
Each admin is a separate email/password account, created exactly as in Section 3.5. To authorize an additional admin, add their UID in TWO places:

10.2.1  In 0-config-admin.js, add it to the ADMIN_UIDS array:

           const ADMIN_UIDS = [
             'FIRST_ADMIN_UID',
             'SECOND_ADMIN_UID'
           ];

       Then publish the changed file - re-upload it on Path A, or re-run firebase deploy on Path B.

10.2.2  In firestore.rules, add it to the isAdmin() list:

           request.auth.uid in ['FIRST_ADMIN_UID', 'SECOND_ADMIN_UID']

       Then Publish the rules in the Firebase console.

BOTH edits are required. Be careful with the punctuation, especially the apostrophes and the comma(s).  They needs to be exactly as shown above That single isAdmin() list controls the analytics dashboard AND admin-only actions such as Force Close. The admin.html and analytics.html pages themselves need no changes.


10.3  CHANGING YOUR ADMIN EMAIL OR PASSWORD
------------------------------------------
On admin.html, signed in, use the "Change sign-in credentials" panel. Enter your current password (required), then a new email address and/or a new password.

10.3.1  A PASSWORD change takes effect immediately.
10.3.2  An EMAIL change sends a confirmation link to the NEW address, and the email only switches after you click that link. An email change therefore requires a real, reachable inbox.

Your account's UID does not change, so ADMIN_UIDS and the security rules stay exactly as they are. There is nothing else to edit.

If you would rather not use a real inbox, you can instead create a brand-new admin account in the Firebase console and swap its UID in. But a new account has a NEW UID, so you must update both places - see Section 10.2.


10.4  GLOBAL SIGN-OUT (all your devices)
---------------------------------------
Signing out from the admin bar signs out that browser AND marks your other admin sessions to require a fresh login the next time they load or refresh an admin page. It is per-admin: signing yourself out never affects a different admin.

It takes effect on the next page load or refresh of the other session, not instantly on an idle, untouched tab. Changing your admin password also invalidates all other sessions.


10.5  THE ADMIN PANEL  (admin.html)
----------------------------------
  Registered Users - only populated when persistUsernames is true (Section 9.1). With the default of false, handles live only on each participant's own device, so this list is empty by design.

  Active Hunts - lists the hunts that are still running.

  Closed hunts awaiting cleanup - appears only when there is something in it. A hunt is normally deleted by its creator's own browser at the moment it closes; if that browser was shut or offline just then, the record survives. Those leftovers are listed here so you can clear them, rather than being counted among the active hunts.

  Force Close - immediately closes a hunt and deletes its data. This requires the isAdmin() rule to be published (Section 5).

  Blocked Usernames - shows the current block list. The list itself lives in the file blocked-usernames.txt: one name per line, and lines beginning with # are comments. To CHANGE the list you edit that file and publish it - see Section 10.9, because how you do that differs by hosting path.

  Map Hosting - shows the map address currently configured and offers a "Check map hosting" button. One click tests that the file is reachable, that your host answers HTTP Range requests, and that the file is a valid PMTiles v3 archive (which is different from the PROTOMAPS BASEMAP v4 schema mentioned in section 2.4.5), then reports which of those failed. Section 8.6 lists what each result means. If mapDownloadUrl is set (Section 9.1), a link to ready-made map areas appears beneath it.

  Change sign-in credentials - see Section 10.3.


10.6  THE ANALYTICS DASHBOARD  (analytics.html)
----------------------------------------------
An anonymous, read-only summary of usage: totals (hunts, participations, bearings by source), rollups (average participants, average hunt length, how often a hunt produced an estimate), charts, and a per-hunt table.

In keeping with the application's spirit of anonymity, locations are deliberately coarse - about a 12.5-mile grid - and no names, exact positions, or times are stored.

The dashboard is READ-ONLY. To clear or reset analytics, delete the "analytics" and "analyticsHunts" collections in the Firebase console.  Firebase will create new "analytics" and "analyticsHunts" collections with the next hunt.  There is no danger in deleting these collections, except that it will permanently reset your analytics.


10.7  CUSTOMIZING THE ACCOUNT EMAILS
-----------------------------------
By default, Firebase's verification and password emails say "...for <your-project-id>" and are signed "Your <your-project-id> team". To brand them:

10.7.1  Set the project's public-facing name, at Settings > Project settings >
        General > "Public-facing name":

        https://console.firebase.google.com/project/PROJECT-ID/settings/general

        Set it to your club or product name. The emails will then read "...for <Your Brand>" and "Your <Your Brand> team".

10.7.2  Or edit the templates directly: Authentication > Templates > choose the email type > the pencil icon. You can adjust the sender name, the subject, and for some types the message body. Firebase allows only limited formatting.


10.8  CLEANING UP ANONYMOUS USERS
--------------------------------
Every participant browser creates an anonymous account in Firebase > Authentication, and over time these accumulate under Authentication > Users. They hold no important data - hunt data is stored separately and purged when a hunt closes - so they are safe to delete manually. A browser that loses its anonymous account simply gets a new one on its next visit.  However, if the automatic deletion of anonymous users was enabled in section 3.3.3.1 then you will never have to manually delete these user by hand.  But if the functionality was not enabled during setup then you will be required to enable a one-time, free upgrade of your project to "Firebase Authentication with Identity Platform". Once enabled, anonymous accounts older than 30 days are deleted automatically, and anonymous sign-in no longer counts toward usage limits or billing quotas.

To upgrade and turn it on (Google changes its menus periodically; this is the general path):

10.8.1  Go to your project's Authentication settings.

        https://console.firebase.google.com/project/PROJECT-ID/authentication/settings

        In the menus: Authentication, then the "Settings" tab.

10.8.2  Look for an option or banner to "Upgrade to Firebase Authentication with Identity Platform" and follow it. Currently, this is found under "Blocking Functions" and "User Activity Logging".  There is a free tier, and you do not need a paid plan for this app's usage. If you cannot find it under Authentication, you can also upgrade from the Google Cloud console under "Identity Platform".

10.8.3  After upgrading, return to Authentication > Settings. Find the anonymous-user clean-up option - often under "User account management" or a similarly named heading - and enable "Auto-delete anonymous users" (30 days).

10.8.4  Save.

Notes:
10.8.5  After you enable it, EXISTING anonymous accounts become eligible for deletion 30 days later; new ones, 30 days after they are created.
10.8.6  This is optional housekeeping. The app runs perfectly well without it. It simply keeps the Users list tidy and stops anonymous sign-ins counting against quota.
10.8.7  It never affects your email/password ADMIN accounts. Only anonymous ones.
10.8.8  Turning it off later leaves any already-scheduled deletions scheduled.

 SECTION 11 - UPDATING TO A NEWER BUILD   (read before you update!)
============================================================

11.1  PRESERVE YOUR OWN FILES
-----------------------------
When you install a newer build, DO NOT blindly overwrite everything, or you will wipe your settings. PRESERVE these four files, which hold YOUR values:

     0-config-firebase.js  your Firebase credentials
     0-config-admin.js     your ADMIN_UIDS
     0-config-foxhunt.js   your branding, content, units, thresholds
     0-config-license.js   your site key

Overwriting 0-config-license.js is the easiest of the four to do by accident, because unlike the others it is a single line and looks unimportant. If it happens, the app will tell you no site key is installed - paste your site key back in and you are done.

setup.html is NOT one of these. You visit it in a browser but never edit it, so it carries nothing of yours and a newer build should replace it - keeping an old copy would leave you with a stale activation page.

Also preserve anything else you added or changed yourself: a replaced favicon.svg, a background image, an edited blocked-usernames.txt, and your .pmtiles map file if you keep it in the app folder.

Everything else - the .html pages, foxhunt.js, foxhunt-theme.js, foxhunt.css, sw.js, and the rest - can be replaced freely.

A newer build sometimes ADDS new settings to 0-config-foxhunt.js. Your existing file will keep working (the app falls back to sensible defaults for anything missing), but to use a new feature you may need to copy its new key across from the new build's 0-config-foxhunt.js into yours. Build notes will say when this applies.


11.2  UPDATING ON PATH A (your own web host)
--------------------------------------------
Two safe approaches - pick either:

11.2.1  Upload the new build over the old, then re-apply your saved copies of the four files listed in Section 11.1; OR
11.2.2  Upload everything EXCEPT those four files.

Keep .htaccess in place (Section 6.2).


11.3  UPDATING ON PATH B (Firebase Hosting)
-------------------------------------------
Your LOCAL app folder is the master copy of your site. You update that folder, then publish it. Keep it - do not delete it after your first deployment.

11.3.1  Copy the new build's files into your local app folder, EXCEPT the four files in Section 11.1, which you keep as they are.

11.3.2  Keep the new build's firebase.json. The one in the new build is correct and current - it is the same file you restored in Section 7.7. This is one file you SHOULD take from the new build.

11.3.3  Keep your existing .firebaserc. This small file records which Firebase project you deploy to. It was created by firebase init, is not part of the build, and should simply be left alone. If it is missing, deployment will not know where to send your files.

11.3.4  You do NOT need to run "firebase init" again. EVER. Init is a first-time-only step, and re-running it would overwrite firebase.json again (Section 7.7). Just deploy.

11.3.5  From the app folder, run:

            firebase deploy

        That is the entire update. Your site is live within a minute or so.

11.3.6  The .htaccess file in the package is ignored by Firebase Hosting. You may leave it in the folder; it does nothing there.


11.4  AFTER UPDATING (both paths)
---------------------------------
Do ONE hard refresh - Ctrl+F5 - or close and reopen the tab. The app updates through a service worker that takes over on the next load, so a single refresh ensures that you and your users see the new version immediately.

If a build's notes say the security rules changed, re-publish firestore.rules as well, keeping your admin UID or UIDs in isAdmin() (Section 5).

 SECTION 14 - LICENSE / ACTIVATION

HOW YOU GET YOUR SITE KEY
You buy Fox Pursuit on Gumroad and receive a LICENSE KEY on your receipt. You open setup.html in your browser on your own site and paste that key into the box on the page (Section 8.2); your purchase is checked once, and your site is issued a permanent SITE KEY beginning with "FP1".

Keep BOTH. The Gumroad license key is your proof of purchase and lets you recover your site key at any time. The site key is what actually licenses your site.

YOUR LICENSE IN ONE PARAGRAPH
Your site key lives in 0-config-license.js (Section 8.2) and travels with your site. Every device that loads your pages is licensed by it automatically, so participants never enter anything and never need a key of their own. The key does not expire, covers this site, and includes free updates.

HOW THE CHECK WORKS
Your key carries its own proof. It was signed by the seller, and every copy of Fox Pursuit carries the matching public key - which can check a signature but cannot create one. So, the app verifies your license with mathematics alone, inside the browser, with no license server and no internet connection.

That has a consequence worth stating plainly: nothing about your license depends on anyone remaining in business. If the seller's website disappears, if Gumroad closes, if this project is abandoned entirely - your installation keeps working, unchanged, indefinitely. There is no server to go down, no subscription to lapse, and no check-in that can fail. This was a deliberate design decision made by the author, and Section 2.4 applies the same thinking to your area maps.

WHAT YOU CAN DO WITHOUT ASKING ANYONE
  - Replace or wipe a device. Nothing to re-enter; the key is in your site, not in a browser.
  - Move to a different web host or a different domain. Copy your files across, including 0-config-license.js, and the app runs. No transfer request, no reactivation, no contact with the seller.
  - Add participants. There is no device count and nothing to register.

WHAT REQUIRES HTTPS
The license check needs the cryptography that browsers only provide over a secure connection. Over plain http the app shows a wall explaining this rather than running unverified. See Section 8.

IF YOUR KEY IS REFUSED
The app names the specific fault rather than giving a generic failure:
  - "No site key has been installed" - the file still holds its placeholder.
  - "could not be verified... may have been truncated" - the key is incomplete. Copy the WHOLE key again; it is about 150 characters and easy to cut short.
  - "0-config-license.js could not be read" - the file has a syntax error, almost always a key pasted across several lines. It must be on one line.
  - "not a Fox Pursuit site key" - something else was pasted in. A site key begins with FP1. and contains two dots within the string.

Open setup.html in your browser on your own site and it will diagnose any of these: paste your key into the box and it will either confirm it or tell you what is wrong with it.

IF YOU LOSE YOUR SITE KEY
Look in the 0-config-license.js of any working deployment you still have, or wherever you saved it at Section 8.2.3. Failing that, open setup.html in your browser and paste your GUMROAD LICENSE KEY into the box again: the same site key is returned, not a new one, so you can recover it yourself as long as the license service is running. Failing all three, contact the seller with your purchase details.

This is the reason Section 8.2.3 asks you to save the site key: it is the copy that depends on nobody.

YOUR LICENSE COVERS ONE PRODUCTION SITE
Because your site key lives in your own files, nothing technically prevents you from running more. The app has no license server and cannot be switched off remotely - that is deliberate, and explained above. It is a trade made in good faith, and these terms are the other half of it.

Fine:
  - A sandbox or test site alongside your production site.
  - Two sites running at once for a short while when you move hosts or domains.
  - Rebuilding your installation as often as you need to.

Not fine:
  - More than one production site on a single license.
  - Passing the files to another club or group to run their own site.

Activations are recorded when they happen, including the domain, and while this project is maintained that record is reviewed from time to time. A future version may also record - from the admin page only - the domain and license ID of installations in use. That is a record for the seller; nothing about running the app will ever depend on it.

If a license appears to be used beyond these terms, expect an email first. Continued use beyond them ends support and updates, and future purchases may be declined. Your installation will not be switched off; there is deliberately no mechanism to do that. Adding one would break the guarantee that makes this software worth owning.  That is, the ability for the application to continue working after maintenance is gone.

 SECTION 15 - TROUBLESHOOTING
============================================================

"This site is not finished setting up" on the sign-in screen, mentioning the Firebase configuration.
    Your 0-config-firebase.js still holds placeholder values, or the values are wrong or incomplete. Paste the real firebaseConfig block from Settings > Project settings > General > "Your apps" (https://console.firebase.google.com/project/PROJECT-ID/settings/general). See Section 4.1. On Path B, remember to re-run firebase deploy after fixing the file - editing it locally is not enough. Verify what actually reached your server using Section 8.1.

"This site is not finished setting up" on the sign-in screen, mentioning sign-in methods.
    One of the two required sign-in providers is switched off in your Firebase project. Enable BOTH Anonymous and Email/Password under Authentication > Sign-in method (Section 3.3). Anonymous is the one usually missed. Nothing in your config files needs changing for this.

setup.html says the license service could not be reached.
    Activation is the one step that needs an outside service. Check your internet connection and try again in a few minutes. Your purchase is unaffected, and nothing about an already-activated site depends on that service. If it keeps failing, contact WA0MCS with your purchase details and a key will be sent directly; it goes in the same box.

setup.html says your purchase could not be verified.
    Check that you copied the WHOLE key from your Gumroad receipt and nothing else - no spaces, no surrounding text. If it still fails, and especially if the purchase was refunded or charged back, contact WA0MCS.

"This site must be served over HTTPS."
    Your address begins http:// rather than https://. The app deliberately stops here: over plain http the browser withholds location, compass, offline storage and the cryptography the license check needs, so the app cannot work properly even if it appeared to start. Install a certificate - most hosts provide one free - and load the site with https. Firebase Hosting (Path B) does this automatically. See Section 8.

"No site key has been installed."
    0-config-license.js still holds PASTE_YOUR_SITE_KEY. You have not activated yet, or the line was never pasted in. See Section 8.2.

"The site key ... could not be verified" / "may have been truncated".
    The site key is incomplete - the usual cause is copying only part of it. It is about 150 characters. Copy the whole thing and paste it again. Open setup.html in your browser to confirm before uploading.

"0-config-license.js could not be read."
    That file has a syntax error, and almost always the cause is a site key pasted across several lines. The whole key must sit on ONE line between the quotation marks. This can also happen to a perfectly good key that an email client wrapped - join the lines back up.

"The value in 0-config-license.js is not a Fox Pursuit site key."
    Something other than your site key was pasted in. A site key begins with FP1. and contains two dots. Your GUMROAD license key does NOT go in this file - you type it into setup.html in your browser, and setup.html gives you the site key that does go here.

"Your PRIVATE key is in 0-config-license.js." (sellers only)
    This message is for whoever issues site keys, not for buyers. If you see it, act on it immediately - see Section 14.

"This account is not an admin. UID: ..."
    The signed-in UID is not in ADMIN_UIDS in 0-config-admin.js. Put that exact UID in ADMIN_UIDS, publish the file, and hard-refresh. After any upgrade, confirm ADMIN_UIDS was not overwritten (Section 11.1).

Analytics dashboard: "Missing or insufficient permissions."
    The signed-in admin UID is not in the isAdmin() list in your PUBLISHED rules. Add it to isAdmin() - and to ADMIN_UIDS - and Publish (Section 5). Note that admin.html can work while analytics.html fails; analytics needs the isAdmin() rule specifically.

Force Close: "Missing or insufficient permissions."
    Same cause. Your published rules do not include the isAdmin() allowance on submission deletes. Re-publish the included firestore.rules with your UID in isAdmin().

New files published, but you still see the old version.
    The service worker is serving the cached build. Hard-refresh (Ctrl+F5), or close and reopen the tab once (Section 11.4).
    On Path B, if this keeps happening to everyone and never resolves, suspect firebase.json. Confirm it still contains the "headers" block naming sw.js (Section 7.6), and re-deploy.

sw.js does not appear in the browser's Network tab at all.
    The app is failing before it registers the service worker. That almost always means a credentials problem - see the api-key-not-valid entry above. Get the app working first, then re-check sw.js.

Map or compass does not work.
    You must be on HTTPS. On http:// the browser blocks GPS, compass, and offline caching. Firebase Hosting is always HTTPS; on your own host, enable it.

The map will not zoom out any further.
    That is deliberate. Your .pmtiles file covers a fixed area, and beyond it there is no map to draw, so the app stops the zoom-out where your coverage ends rather than showing fragments against white. To zoom out further, build a .pmtiles covering a larger area (Section 2.3).

The map area says "Map not configured."
    tileUrl in 0-config-foxhunt.js is blank or still the placeholder. Set it to the address of your hosted .pmtiles file (Section 4.4). On Path B, re-run firebase deploy after editing.

A participant's saved offline area shows as "no longer usable."
    They downloaded it from a different map than the one now being served - most often because the served .pmtiles was changed (Section 2.2.3). The saved area cannot be used with a different map; they tap Remove to reclaim the space and download again for the current area. Offline areas are also per browser, so an area saved in one browser will not appear in a different browser on the same phone.

The map is blank or grey, but the rest of the app works.
    Almost always the map-data file: the host is not answering HTTP Range requests, the tileUrl address is wrong, the file is on a different domain without CORS, or the file was corrupted in upload. Do not guess - open the admin page and press "Check map hosting" (Section 10.5), which will tell you which of those it is. See also Section 2. (This is different from the "Map not configured" notice above: that notice means tileUrl is unset; a blank map means tileUrl is set but the file cannot be read correctly.)

A blank page instead of the site (Path A).
    Your host may have placed an empty index.php in the folder, and it is being served ahead of index.html. See Section 6.2.

Verification emails show the wrong name.
    Set your project's public-facing name (Section 10.7).

Authentication > Users is full of anonymous accounts.
    Normal - one per participant browser. They are safe to delete, or you can enable automatic clean-up (Section 10.8). Never delete your admin account.

The app will not load after you edited 0-config-foxhunt.js.
    A renamed key, or a missing comma or quotation mark, breaks the file. Undo your last edit. Change only the VALUES inside quotes.

"'firebase' is not recognized..." (Path B).
    Close the command window entirely and open a fresh one. A newly installed command is not visible to a window that was already open. If it still fails, re-run: npm install -g firebase-tools

firebase deploy published the wrong thing, or an empty site (Path B).
    You almost certainly ran it from the wrong folder. Every Firebase command must be run from the folder that contains the app files. Confirm with "dir" that you can see firebase.json before deploying (Section 7.4).
